Moving the domain to Cloudflare

The cutover.

Everything the club runs on encinovelodrome.org is steered by one small settings file. To publish the new website we need to move that file from GoDaddy to Cloudflare. The website is not what's at risk. Email is. This page explains why, and exactly how we avoid it.

01 · Plain English

What we are actually doing

Think of the domain name as an address book that tells the rest of the internet where to find things. One line says "the website lives here." Another says "email for this domain goes there." Others prove to other mail systems that our email is really ours.

Right now that address book is kept at GoDaddy. We want to keep it at Cloudflare instead, because Cloudflare is free, faster, and is where the new website will be published from. The domain stays yours and stays registered at GoDaddy. Only the address book moves.

Here is the important part: we are not changing the website in this step. The current Zoho site keeps running exactly as it does today. We copy the address book across letter for letter, change nothing anyone can see, and confirm it all still works. Only later, when the new site is ready, do we change the line that points at the website.

Cost

Nothing

Cloudflare's free plan covers everything the club needs. No new bills, and no change to the GoDaddy registration you already pay for.

What members notice

Nothing, if it goes right

The website stays up. Email keeps arriving. The calendar, the donation links and BikeReg are all untouched — none of them depend on this.

02 · Plain English

The one real risk, in one page

There is exactly one way this migration quietly hurts the club, and it is worth understanding before you approve it.

A hidden note in the old address book

Alongside "email goes to Zoho," the club's address book contains a second entry whose job is to vouch for your email — to tell Gmail, Outlook and the rest that a message claiming to be from board@encinovelodrome.org is genuine. Without it, your mail looks suspicious to spam filters.

That vouching entry does not sit on its own. It points at another entry that also lives inside the old address book, one GoDaddy created automatically. If we copy the obvious lines across and miss that one, the chain snaps.

Nothing breaks loudly. Email still sends. It just starts failing its trust check, and over days it slides into other people's spam folders — inspection requests, board mail, donation receipts — with no error message and no obvious cause.

I found it by reading the live settings rather than assuming, and it is written into the record set as a required line. This page exists mostly so that this one thing cannot be forgotten.

Two other things worth knowing

While checking, I found the club's email is missing two protections that most organisations have. Neither is caused by this move, and neither is urgent, but both are easy wins while we are in here.

  • No DKIM. This is a second, stronger signature on outgoing mail. Zoho can switch it on from your admin console. Right now the club's email is vouched for one way instead of two.
  • No DMARC. This is the instruction that tells other mail systems what to do with messages that fail the checks, and it reports who is sending mail using your name. I have included a monitoring-only version that changes nothing about delivery and simply starts collecting that information.
03 · Plain English

What I need, and what happens when

From Roger

Approval, and a quiet window

Say go, and pick a day that is not a race day and not the day before a big mailing. A weekday morning is ideal.

Also: a decision on whether we turn on the two email protections above at the same time. My recommendation is yes.

From Vinh

Cloudflare account and a scoped key

Create the free Cloudflare account, add the domain, and generate an API token limited to editing DNS on this one zone. Then change the nameservers at GoDaddy when we are ready.

Everything else is scripted and reviewable before it runs.

The shape of the day

  1. Beforehand — no visible change

    Cloudflare account created, domain added, and the full address book loaded in exactly as it is today. Nothing is live yet. Nothing has moved.

  2. The switch — about five minutes of work

    Vinh changes two settings at GoDaddy. From that moment the internet gradually starts reading the new address book instead of the old one. Because both say the same thing, nobody notices.

  3. Settling — a few hours, up to two days

    Different parts of the internet update at different speeds. During this window some computers use the old book and some the new. Since both are identical, this is uneventful. We check email and the website through it.

  4. Later — the new website

    Once the new site is built and approved, one line changes to point at it. That is a separate day, and it is quick to undo.

If something goes wrong

We put the GoDaddy nameservers back, and the old address book takes over again. The safety net is that we never delete anything at GoDaddy during the move — the old copy sits there untouched. The one caveat worth stating plainly: reversing a nameserver change is not instant. It can take a few hours to fully unwind, which is exactly why phase one changes nothing visible, so we are never racing a clock with a broken site.

07 · Technical

Running it

The script dry-runs by default and prints every create and update before doing anything. It never deletes without --prune, and refuses to prune MX or mail TXT records at all.

# scoped token: Zone.DNS Edit, this zone only
export CLOUDFLARE_API_TOKEN=...

./apply-dns.sh                 # dry run — shows the plan, writes nothing
./apply-dns.sh --apply         # commit phase 1 parity

# ...now change nameservers at GoDaddy to the two Cloudflare gives you...

./apply-dns.sh --verify        # reads live DNS back; needs no token

# later, once the new site is approved:
./apply-dns.sh --phase 2 --host <project>.pages.dev --apply

What good looks like

  • Nameservers answer as Cloudflare, and --verify shows the same A, MX and TXT values as section 4.
  • SPF resolves through two hops: apex → dc-8e814c8572._spfm → zohomail.com. If the middle hop returns nothing, stop and fix it before anything else.
  • Send a test message from board@ to a Gmail address. Open Show original and confirm SPF: PASS. This is the check that actually matters.
  • The site still loads on both the apex and www, and still serves from Zoho.

Rollback

  • Point the nameservers back to ns65 / ns66.domaincontrol.com. The GoDaddy zone is never deleted during this migration, so the old records are still sitting there.
  • Expect hours, not minutes — nameserver delegation is cached by the registry, up to 48 hours in the worst case. This is the reason phase 1 changes nothing visible: there is no outage to race.
  • For phase 2, rollback is just restoring the two Zoho A records and the www CNAME, which moves at record TTL — minutes if you lowered them first.

How this was produced. Every record in section 4 was read from live DNS over DNS-over-HTTPS on 10 September 2026 — nothing here is copied from documentation or assumed from a provider's defaults. The SPF dependency was found by resolving the include chain rather than reading the apex record alone. The absence of DKIM was established by sweeping eleven common selectors; a selector in use under a name outside that list would not have been detected, so confirm in the Zoho admin console before concluding DKIM is off. Record values, the apply script and the raw inventory were delivered alongside this page as records.json, apply-dns.sh and dns-inventory.txt. Prepared by Michael Bowers, Heed Business Solutions.
